## 2026-07-24 — Sync-mechanics constraints worth keeping in view

- **Guard pin bootstrap:** `provides/github/workflows/foundation-guard.yml` pins repo-foundation by commit (`ref:`). The pin must be bumped to a main commit that carries the `--guard` engine after the sync-mechanics branch merges and BEFORE the first sync ships the guard to consumers; at a pre-guard pin the check fails on the unknown option. Ongoing rule: a manifest or engine change the guard must see requires a pin bump, delivered by the next sync (the sync is the pin's writer).
- **Dependabot vs the guard (maintainer ruling, 2026-07-24):** Dependabot PRs are exempt from the foundation guard — a consumer may merge a pinned-action bump (security fixes especially) ahead of the canonical sync. Consequence to expect: until repo-foundation bumps the same pin, a sync run renders the older canon and would open a converge-PR proposing the revert — so bump promptly in RF when a consumer takes a Dependabot bump on a canonical workflow.
- **Exec-bit drift heals (behavior as of the sync-mechanics branch):** the engine compares git file modes as well as content — a content-identical `chmod` drift syncs back as a `status: mode` change (the Git Data tree entry carries the correction), and the guard and audit both flag it. The synced lint-perms CI remains the consumer-side backstop.
- **Vale rule files must stay `.yml`, and the failure is silent.** Verified in Vale source (`internal/check/manager.go`): `addRuleFromSource` only acts on names ending `.yml`, and the individual-rule loader builds `<Rule>.yml` directly. A rule file renamed to `.yaml` raises no error — it is simply never loaded, so the style disappears and the prose gate passes everything. This is the one verified exception to the org's `.yml` → `.yaml` convention; `dependabot`, `zizmor`, `copilot-setup-steps`, and Actions workflows all accept either extension (checked against upstream source 2026-07-25).
- **Engine child processes in specs:** spawn `RbConfig.ruby`, never bare `ruby` — a bare name resolves through PATH to the frozen macOS system Ruby 2.6. BSD `env -P` locates only the utility and does not export the modified PATH to children; `brew exec` does provide portable Ruby but strips `TMPDIR`, which in the Claude Code sandbox pushes `Dir.mktmpdir` into the repo root where `git init` trips the `.git/hooks` write denial — so in-sandbox suite runs use `env -P… PATH=… bundle exec rspec`. (Promoted to `.ai/org/memory.md` 2026-07-25; it constrains every Ruby repo in the org, not just this one.)

## 2026-07-25 — Shell that has to survive `brew style` (from rf-upstream-notes §§ 2, 9, 12e, 12f)

Migrated out of `docs/handoff/rf-upstream-notes.md` at the canonical-repairs session, which closed that document. These four are the durable half of its Homebrew findings; they bite whenever a repo-foundation `.sh` canonical lands in a Homebrew-aligned consumer, because `brew style` runs over it there.

- **Homebrew's shfmt wrapper corrupts heredoc bodies.** `brew style [--fix]` applies the post-shfmt transforms in `Library/Homebrew/utils/shfmt.sh` (`wrap_then_do`, `align_multiline_if_condition`, and the other line-based regex rewrites) to *every* line of a file, tracking no heredoc state. Observed: content lines re-indented, Python bodies flattened, terminators indented so the here-document never closes, following functions absorbed into it, and false "fixable bad styles" reports on valid scripts. shfmt itself is fine — the corruption is Homebrew's post-processing. This is what destroyed `scripts/lint-unicode.sh`'s embedded detector, and the reason it now lives in `scripts/lint-unicode.py`. **Practical rule: keep heredocs out of org `.sh` canonicals.** The upstream fix (a heredoc state machine in the transform loop) is a queued Backlog item, not a blocker.
- **`brew style --fix` rewrites POSIX `[ ]` to `[[ ]]`.** It applies ShellCheck's SC2292 auto-fix across any un-exempted file, silently de-POSIX-ing a script that has to keep running under dash on the Ubuntu runners. A canonical POSIX `.sh` landing in a Homebrew-aligned repo therefore needs the numeric-disable header, or a routine `--fix` pass breaks it.
- **There is no per-file shfmt exemption available to us.** shfmt honors EditorConfig `ignore = true` when walking directories, and `--apply-ignore` extends that to direct-file runs — but any explicit parser or printer flag makes shfmt discard EditorConfig entirely, and brew's `style.rb` passes `--language-dialect bash --indent 2 --case-indent` plus explicit file lists, with its only exclusions hardcoded. So no consumer-side `.editorconfig` entry can exempt a file from `brew style` today (mvdan/sh#1037 plus the shfmt man page). The org-side answer is the sync-time formatting mutation, not a consumer-side opt-out.
- **Never begin a comment line with lowercase `# shellcheck`.** The directive parser claims it and errors (SC1072/SC1073) — so a comment *about* ShellCheck, which org policy requires above every disable line, must word-wrap so the name lands mid-line, or write "ShellCheck" (the parser matches lowercase only).

## 2026-07-26 — Guard-pin freshness is CI-enforced

The 2026-07-24 standing rule ("a manifest or engine change the guard must see requires a pin bump") is now held by `.github/workflows/guard-pin.yml` (repo-foundation-only, not in the manifest), after the invariant broke in PRs #11 and #12 back to back. It fails any `main` push where a commit in `pin..HEAD` touches `sync-manifest.yaml` or `.github/actions/sync/`, and its failure message prints the exact `ref:` to set. Expected behavior, not a bug: `main` goes red between a pin-relevant merge and the bump PR — including immediately after PR #12 itself merges. Branch-side automation of the bump (hook or sign-push step) was evaluated and rejected: a commit cannot contain its own hash, re-signing rewrites the SHAs a hook would have recorded, and concurrent branches have no correct branch-side answer. Full analysis in ADR 0024.

## 2026-07-28 — What syncs, and how a repeated bot finding gets settled

- **The doc-distribution criterion is in `docs/repo-standards.md`, and deliberately is NOT an ADR.** ADR 0004 keeps org-wide decision records in repo-foundation because an ADR's identity is a number in one sequence and copies would fork the numbering contract `adrs doctor` enforces — a reason that does not generalize to ordinary docs, whose only risk (drift) the sync and the guard already handle. So 0004 stands unamended and the standards page carries the three genres. A future session that reads the absence of an ADR as an oversight should stop here: it was ruled on 2026-07-28.
- **The test for an operational how-to is "does someone working in the consumer repository need this during routine work?"** Anything the synced CONTRIBUTING baseline links to passes almost by definition — a CONTRIBUTING that sends a contributor to another repository for its own instructions fails offline. Worked example: `docs/testing-github-workflows-locally.md` rides `ci_core` because it documents the workflows that set delivers.
- **A review-bot finding declined twice on "it works on this machine" grounds is a signal to re-read, not to decline again.** CodeRabbit twice flagged the bidi scan's locale; both declines were correct about the stated claim (`C.UTF-8` exists here) and wrong about the defect underneath — a bracket expression is a set of *characters* and degrades to a set of *bytes* without a UTF-8 locale, matching the `E2` lead byte of every U+2xxx character, so an em dash tripped the gate (measured). The scan now uses `grep --fixed-strings` under `LC_ALL=C`.
- **Where a settled finding lives is `.coderabbit.yaml` `path_instructions`**, with the *reason* written out, not the ruling alone. That file is the org's standing answer to bots; a finding argued down in a PR thread and not recorded there returns on the next PR.

## 2026-07-29 — Workstream labels, and two gates that lie about why they failed

- **`W<n>` means a WORKSTREAM in `workspace/master-plan.md`, never a week.** W1 is the repo-foundation build-out, W6 is the sandbox script rename to `isolate enter --level=N` over five levels (`host`, `restricted`, `detached`, `contained`, `virtualized`). Reading them as calendar weeks makes a scheduling claim the plan never made.
- **The `AGENTS.md` rspec recipe needed `PATH` passed twice, and the doc had drifted from the fact.** BSD `env -P` uses the alternate path only to locate the utility it runs, so `env -P"<portable-ruby>:$PATH" bundle exec rspec` leaves every spawned child on the frozen system Ruby 2.6; one integration example then fails loading a bundler built for 4.0. Measured 2026-07-29: documented form 210 examples / 1 failure, `env -P"$RB:$PATH" PATH="$RB:$PATH" …` 210 / 0. The mechanism was already in `.ai/org/memory.md` from 2026-07-25; only the build block was stale. A suite failure that names a gem loader is this, not your change.
- **Read the crash report before theorizing about a crash.** lume 0.5.0's `lume create` trap printed `Pre-VZMacHardwareModel: hardwareModel=132 bytes` as its last line, which reads as a hardware-model failure and is not: `~/Library/Logs/DiagnosticReports/*.ips` named `_dispatch_assert_queue_fail` under `-[VZMacOSInstaller initWithVirtualMachine:restoreImageURL:]`. The `.ips` files are JSON after a one-line header (`tail -n +2 … | jq`), and the faulting thread's frames settle in one step what source reading only narrows. Reported as trycua/cua#2670.
- **`act --pull=true` is a manifest check, not a download.** A warm run logs `Status: Image is up to date` and transfers nothing, so no local image cache with a TTL is warranted; `--rebuild` is for Dockerfile-based local actions, `--reuse` keeps container state (declined for the same reproducibility reason as reusing a lume guest), and `--rm` only affects the failure path. Verified against a real container run on 2026-07-28.

## 2026-07-29 — The unicode gate is one script; a false premise caught by the neighbors

- **Scope is the policy unit; entry points are triggers.** `scripts/lint-unicode.sh` implements all three scopes (`--scope=staged|tracked|tree`); the `80-unicode` plugin, the `lint-unicode` CI job, and the `unicode-audit` workflow are just callers. The staged scope scans INDEX content via `git checkout-index --prefix --stdin -z` — materialized into a temp tree so findings report logical paths and `bidi-allow:` is read from the blob. A worktree edit, staged or not, never changes what the staged scope sees.
- **"The plugin must stay dependency-free" was a false premise I wrote and then cited.** `10-shell` and `80-perms` already called into `scripts/`; the claim survived two rounds because it sat in `.coderabbit.yaml` and the ADR looking authoritative. Checking the sibling plugins took one grep. When a rationale sounds structural, verify it against the neighbors before repeating it.
- **The unsigned-tail hazard is real: PR #17 merged without its last three commits.** They sat unsigned on the parked branch; the fold was to branch from the parked tip (their parent was already on main), not cherry-pick. Check `git log @{u}..HEAD` before declaring a PR merged-and-done, and treat "sign-push, THEN merge" as ordered.
- **The unicode-audit matrix trial has a sunset**: ~20 runs or a month of decision-column agreement → drop the macos leg, promote the workflow to ci_core with per-ecosystem dep steps, remove spec.yml's interim tree step in the same change. Recorded in the workflow header and ADR 0006; do not let the matrix become furniture.
