## 2026-07-24 — Sync-mechanics constraints worth keeping in view

- **Guard pin bootstrap:** `provides/github/workflows/foundation-guard.yml` pins repo-foundation by commit (`ref:`). The pin must be bumped to a main commit that carries the `--guard` engine after the sync-mechanics branch merges and BEFORE the first sync ships the guard to consumers; at a pre-guard pin the check fails on the unknown option. Ongoing rule: a manifest or engine change the guard must see requires a pin bump, delivered by the next sync (the sync is the pin's writer).
- **Dependabot vs the guard (maintainer ruling, 2026-07-24):** Dependabot PRs are exempt from the foundation guard — a consumer may merge a pinned-action bump (security fixes especially) ahead of the canonical sync. Consequence to expect: until repo-foundation bumps the same pin, a sync run renders the older canon and would open a converge-PR proposing the revert — so bump promptly in RF when a consumer takes a Dependabot bump on a canonical workflow.
- **Exec-bit drift heals (behavior as of the sync-mechanics branch):** the engine compares git file modes as well as content — a content-identical `chmod` drift syncs back as a `status: mode` change (the Git Data tree entry carries the correction), and the guard and audit both flag it. The synced lint-perms CI remains the consumer-side backstop.
- **Vale rule files must stay `.yml`, and the failure is silent.** Verified in Vale source (`internal/check/manager.go`): `addRuleFromSource` only acts on names ending `.yml`, and the individual-rule loader builds `<Rule>.yml` directly. A rule file renamed to `.yaml` raises no error — it is simply never loaded, so the style disappears and the prose gate passes everything. This is the one verified exception to the org's `.yml` → `.yaml` convention; `dependabot`, `zizmor`, `copilot-setup-steps`, and Actions workflows all accept either extension (checked against upstream source 2026-07-25).
- **Engine child processes in specs:** spawn `RbConfig.ruby`, never bare `ruby` — a bare name resolves through PATH to the frozen macOS system Ruby 2.6. BSD `env -P` locates only the utility and does not export the modified PATH to children; `brew exec` does provide portable Ruby but strips `TMPDIR`, which in the Claude Code sandbox pushes `Dir.mktmpdir` into the repo root where `git init` trips the `.git/hooks` write denial — so in-sandbox suite runs use `env -P… PATH=… bundle exec rspec`. (Promoted to `.ai/org/memory.md` 2026-07-25; it constrains every Ruby repo in the org, not just this one.)

## 2026-07-25 — Shell that has to survive `brew style` (from rf-upstream-notes §§ 2, 9, 12e, 12f)

Migrated out of `docs/handoff/rf-upstream-notes.md` at the canonical-repairs session, which closed that document. These four are the durable half of its Homebrew findings; they bite whenever a repo-foundation `.sh` canonical lands in a Homebrew-aligned consumer, because `brew style` runs over it there.

- **Homebrew's shfmt wrapper corrupts heredoc bodies.** `brew style [--fix]` applies the post-shfmt transforms in `Library/Homebrew/utils/shfmt.sh` (`wrap_then_do`, `align_multiline_if_condition`, and the other line-based regex rewrites) to *every* line of a file, tracking no heredoc state. Observed: content lines re-indented, Python bodies flattened, terminators indented so the here-document never closes, following functions absorbed into it, and false "fixable bad styles" reports on valid scripts. shfmt itself is fine — the corruption is Homebrew's post-processing. This is what destroyed `scripts/lint-unicode.sh`'s embedded detector, and the reason it now lives in `scripts/lint-unicode.py`. **Practical rule: keep heredocs out of org `.sh` canonicals.** The upstream fix (a heredoc state machine in the transform loop) is a queued Backlog item, not a blocker.
- **`brew style --fix` rewrites POSIX `[ ]` to `[[ ]]`.** It applies ShellCheck's SC2292 auto-fix across any un-exempted file, silently de-POSIX-ing a script that has to keep running under dash on the Ubuntu runners. A canonical POSIX `.sh` landing in a Homebrew-aligned repo therefore needs the numeric-disable header, or a routine `--fix` pass breaks it.
- **There is no per-file shfmt exemption available to us.** shfmt honors EditorConfig `ignore = true` when walking directories, and `--apply-ignore` extends that to direct-file runs — but any explicit parser or printer flag makes shfmt discard EditorConfig entirely, and brew's `style.rb` passes `--language-dialect bash --indent 2 --case-indent` plus explicit file lists, with its only exclusions hardcoded. So no consumer-side `.editorconfig` entry can exempt a file from `brew style` today (mvdan/sh#1037 plus the shfmt man page). The org-side answer is the sync-time formatting mutation, not a consumer-side opt-out.
- **Never begin a comment line with lowercase `# shellcheck`.** The directive parser claims it and errors (SC1072/SC1073) — so a comment *about* ShellCheck, which org policy requires above every disable line, must word-wrap so the name lands mid-line, or write "ShellCheck" (the parser matches lowercase only).

## 2026-07-28 — What syncs, and how a repeated bot finding gets settled

- **The doc-distribution criterion is in `docs/repo-standards.md`, and deliberately is NOT an ADR.** ADR 0004 keeps org-wide decision records in repo-foundation because an ADR's identity is a number in one sequence and copies would fork the numbering contract `adrs doctor` enforces — a reason that does not generalize to ordinary docs, whose only risk (drift) the sync and the guard already handle. So 0004 stands unamended and the standards page carries the three genres. A future session that reads the absence of an ADR as an oversight should stop here: it was ruled on 2026-07-28.
- **The test for an operational how-to is "does someone working in the consumer repository need this during routine work?"** Anything the synced CONTRIBUTING baseline links to passes almost by definition — a CONTRIBUTING that sends a contributor to another repository for its own instructions fails offline. Worked example: `docs/testing-github-workflows-locally.md` rides `ci_core` because it documents the workflows that set delivers.
- **A review-bot finding declined twice on "it works on this machine" grounds is a signal to re-read, not to decline again.** CodeRabbit twice flagged the bidi scan's locale; both declines were correct about the stated claim (`C.UTF-8` exists here) and wrong about the defect underneath — a bracket expression is a set of *characters* and degrades to a set of *bytes* without a UTF-8 locale, matching the `E2` lead byte of every U+2xxx character, so an em dash tripped the gate (measured). The scan now uses `grep --fixed-strings` under `LC_ALL=C`.
- **Where a settled finding lives is `.coderabbit.yaml` `path_instructions`**, with the *reason* written out, not the ruling alone. That file is the org's standing answer to bots; a finding argued down in a PR thread and not recorded there returns on the next PR.

## 2026-07-29 — Workstream labels, and two gates that lie about why they failed

- **`W<n>` means a WORKSTREAM in `workspace/master-plan.md`, never a week.** W1 is the repo-foundation build-out, W6 is the sandbox script rename to `isolate enter --level=N` over five levels (`host`, `restricted`, `detached`, `contained`, `virtualized`). Reading them as calendar weeks makes a scheduling claim the plan never made.
- **The `AGENTS.md` rspec recipe needed `PATH` passed twice, and the doc had drifted from the fact.** BSD `env -P` uses the alternate path only to locate the utility it runs, so `env -P"<portable-ruby>:$PATH" bundle exec rspec` leaves every spawned child on the frozen system Ruby 2.6; one integration example then fails loading a bundler built for 4.0. Measured 2026-07-29: documented form 210 examples / 1 failure, `env -P"$RB:$PATH" PATH="$RB:$PATH" …` 210 / 0. The mechanism was already in `.ai/org/memory.md` from 2026-07-25; only the build block was stale. A suite failure that names a gem loader is this, not your change.
- **Read the crash report before theorizing about a crash.** lume 0.5.0's `lume create` trap printed `Pre-VZMacHardwareModel: hardwareModel=132 bytes` as its last line, which reads as a hardware-model failure and is not: `~/Library/Logs/DiagnosticReports/*.ips` named `_dispatch_assert_queue_fail` under `-[VZMacOSInstaller initWithVirtualMachine:restoreImageURL:]`. The `.ips` files are JSON after a one-line header (`tail -n +2 … | jq`), and the faulting thread's frames settle in one step what source reading only narrows. Reported as trycua/cua#2670.
- **`act --pull=true` is a manifest check, not a download.** A warm run logs `Status: Image is up to date` and transfers nothing, so no local image cache with a TTL is warranted; `--rebuild` is for Dockerfile-based local actions, `--reuse` keeps container state (declined for the same reproducibility reason as reusing a lume guest), and `--rm` only affects the failure path. Verified against a real container run on 2026-07-28.

## 2026-07-29 — The unicode gate is one script; a false premise caught by the neighbors

- **Scope is the policy unit; entry points are triggers.** `scripts/lint-unicode.sh` implements all three scopes (`--scope=staged|tracked|tree`); the `80-unicode` plugin, the `lint-unicode` CI job, and the `unicode-audit` workflow are just callers. The staged scope scans INDEX content via `git checkout-index --prefix --stdin -z` — materialized into a temp tree so findings report logical paths and the annotation is read from the blob. A worktree edit, staged or not, never changes what the staged scope sees.
- **"The plugin must stay dependency-free" was a false premise I wrote and then cited.** `10-shell` and `80-perms` already called into `scripts/`; the claim survived two rounds because it sat in `.coderabbit.yaml` and the ADR looking authoritative. Checking the sibling plugins took one grep. When a rationale sounds structural, verify it against the neighbors before repeating it.
- **The unsigned-tail hazard is real: PR #17 merged without its last three commits.** They sat unsigned on the parked branch; the fold was to branch from the parked tip (their parent was already on main), not cherry-pick. Check `git log @{u}..HEAD` before declaring a PR merged-and-done, and treat "sign-push, THEN merge" as ordered. Now encoded in the `tb-session-close` skill.
- **A guard that cannot fire is worse than no guard.** The newline-in-staged-path check was first written as `tr -dc '\n' … | grep -q '.'` — but text consisting only of newlines has no non-empty line, so `grep '.'` never matched and the bypass stayed live. Counting bytes (`| wc -c`) is the form that works. Write the test that proves a guard fires before believing it does; this one was caught by a fixture with a literal newline in its filename. (The guard itself is gone — the pipeline became NUL-delimited end to end, which scans such a path rather than refusing it.)
- **A pipeline is the wrong shape for a security gate's input.** `git diff --cached -z | git checkout-index --stdin -z` reports the LAST command's status, and an empty stdin is a successful checkout-index — so a failed `git diff` produced an empty materialization and an exit-0 scan. Write the list to a file, check that status, then feed it. Both review bots caught this independently.
- **The `unicode-audit` workflow runs on ONE ubuntu runner.** A two-OS matrix was drafted and dropped: local runs and the pre-commit hook exercise BSD `file(1)` on every commit, so CI exercising the GNU build is a second angle on the same tree rather than a duplicate, and the only direction that could hurt — CI skipping what a local run scans — is already covered by the staged scope. Divergence is measured on demand with `act`. Still queued: promotion into `ci_core`, which wants a per-ecosystem dependency step and removes `spec.yml`'s interim tree step in the same change.

## 2026-07-30 — Skills, the formatter grant, and three things that were not what they looked like

- **SPDX goes inside YAML frontmatter, and skills load that way.** Measured and proven both directions; the full record is in `.ai/org/memory.md` (2026-07-30), including the verification method. The trap worth repeating here: a clean `scripts/annotate.sh` run does **not** confirm placement, because it acts only on files `reuse lint` reports as non-compliant and `reuse lint` accepts the strings anywhere. Strip-and-re-annotate a copy, then diff.
- **The agent sandbox has denied ALL Bash access under `<repo-root>/.claude/skills/` — writes, formats, and deletes.** `Write`/`Edit` reach it; `rm` returns `Operation not permitted`, `annotate.sh` cannot annotate, and `rumdl fmt` reports "Fixed 24/26 issues" while changing nothing. Never trust a formatter's exit status inside that tree; re-run the checker. `scripts/annotate.sh` and `rumdl fmt` are now in `sandbox.excludedCommands` to close exactly this, guarded by a `Bash` PreToolUse hook that refuses `annotate.sh` when it differs from `origin/main` or when there is no `origin/main` to compare against. The deny on writing skill *content* stays: a skill is instructions a later session follows, so agent-authored skill text should not be a silent side effect, and excepting two deterministic formatters is the narrower grant. The guard matters because `excludedCommands` runs a command with the sandbox off entirely — an unguarded entry for a repo script would let a session modify that script and then execute it unsandboxed.
- **CodeRabbit reads `AGENTS.md` by default but cannot follow `@docs/agent-principles.md`.** `**/AGENTS.md` and `**/CLAUDE.md` are in its built-in `knowledge_base.code_guidelines.filePatterns` list, so it was reading the pointer and never the principles — which is why org rules kept having to be hand-transcribed into `path_instructions`. Naming the imported file explicitly is the fix; setting that key replaces the built-in list, so the defaults worth keeping must be repeated.
- **PII in continuity files draws its line at what the detail identifies, not at how specific it is.** Repository names, repo-relative paths, symbol names, tool versions, and issue numbers are the evidence an entry exists to carry; generalizing them to "a consumer repository" makes the entry unactionable. Machine-specific absolute paths (`/Users/<name>/…`), personal usernames, and hostnames identify a person rather than a fact, are wrong for every other reader, and `.ai/org/memory.md` syncs to every consumer while ADR text is published. Audited 2026-07-30: `.ai/` and `docs/decisions/` carry none, so the rule is preventive. Both halves are in `.coderabbit.yaml`, one declining a review finding and one conceding it.
- **The Bundler lockfile warning is not a Dependabot omission, and a bare `bundle` cannot even report its version here.** Dependabot's bundler ecosystem updates *dependencies*; nothing manages `BUNDLED WITH`. Bundler self-installs the recorded version and restarts, which keeps local and CI resolving identically — that pinning is the feature, and the cost is one gem install per run. Meanwhile `bundle --version` through `PATH` finds the frozen macOS system Ruby 2.6, which raises `Gem::GemNotFoundException` whenever the lockfile pins a bundler it lacks. So any script probing bundler resolves Homebrew's portable Ruby first (passing `PATH` twice, per the 2026-07-25 org entry) and skips otherwise. `brew exec bundle --version` also works but measured ~1.2s against ~0.23s. `scripts/foundation-doctor.sh` now carries an advisory probe on this: portable Ruby first, then whatever `bundle` PATH resolves — correct on a Linux runner after `setup-ruby`, and self-excluding on macOS without a platform test since the system bundler exits instead of answering. Its fix hint prints the resolved invocation, never a bare `bundle update --bundler`. Deliberately not a pre-commit gate: that would fail for every contributor whose bundler differs, over a warning Bundler already handles.

## 2026-07-31 — A CR in a filename was the same bypass as a newline; and two guards that did not guard

- **`open(path, encoding='utf-8')` silently rewrites CR to LF inside FILENAMES.** Universal-newline translation is on by default in text mode, so the NUL-delimited path list `scripts/lint-unicode.py` reads had `we\rird.txt` turned into `we\nird.txt` — a path that does not exist, dropped at the `is_file()` check, contents never scanned. Exactly the bypass the NUL conversion closed for `\n`, still live for `\r` one layer up. `newline=''` disables the translation and is load-bearing; text mode is still wanted for the UTF-8 decode. Caught by Greptile, reproduced before fixing (a staged file with a CR in its name exited 0), and specced. The POSIX fallback was never affected: `xargs -0` translates nothing.
- **A `PreToolUse` hook that probes with `jq` must fail closed when `jq` is missing.** The guard on `scripts/annotate.sh` began as `if command -v jq …; then cmd=$(…); fi` — so with no `jq` the command string stayed empty, the `case` matched nothing, and the hook exited 0, leaving an unsandboxed command completely ungated. Both the missing-tool and parse-failure paths now exit 2. Blocking every Bash call on a missing `jq` is the proportionate trade: the alternative silently disables a sandbox-escape guard, and macOS has shipped `/usr/bin/jq` since Sequoia (verified present here), so the case is unreachable on any supported macOS.
- **A sandbox grant should name the paths it exists for.** `scripts/annotate.sh *` and `rumdl fmt *` let arbitrary arguments run unsandboxed when the gap being closed was writes under `<repo-root>/.claude/skills/`. Narrowed to the bare `scripts/annotate.sh` (its documented whole-repo invocation, and the only one it needs) and `rumdl fmt .claude/skills/*`. Everything else already formats fine inside the sandbox.
- **`git reset --hard origin/main` does not belong in a routine closing recipe, and the deny list says so.** The routine realignment after a branch lands is `git pull --ff-only`; `reset --hard` is only for the documented case where commits were made on local `main` and re-signed onto a branch, leaving the same trees at two SHAs. It sits in `permissions.deny`, which is the standing signal it is never routine. Recommending it by habit is how a destructive command becomes normalized.
- **A recipe that chains `rm -f` on success consumes its own inputs.** Repeating a previous turn's closing recipe verbatim handed the maintainer `gh pr edit --body-file .ai/scratchpad/pr18-body-updated.md` after the previous turn's recipe had already deleted that file. Re-derive the recipe from current state every time and `ls` every path it names before printing it. Now a step in the `tb-session-close` skill.

## 2026-07-31 — The main-branch guard has a hole, and `lume --detach` lies about success

- **The `PreToolUse` main-branch guard matches `Edit|Write|MultiEdit` and therefore misses Bash.** Discovered by tripping it: after PR #18 merged and the working tree returned to `main`, a `Write` was correctly refused — but the same file had already been edited on `main` minutes earlier through a `python3 - <<'PY'` heredoc in a Bash call, which the guard never sees. Anything that writes through a shell (`sed -i`, `tee`, a Python or Ruby one-liner, `>` redirection) bypasses it completely. The pre-commit hook still blocks the *commit* to `main`, so nothing reaches history, but the working tree gets dirtied on the wrong branch and the recovery is `git switch -c` after the fact. Worth extending the `Bash` matcher that now exists for the annotate guard to cover this, and worth remembering that a guard scoped to tool names is not scoped to effects.
- **`lume run --detach` prints a PID and exits 0 before the VM has started.** It re-executes lume under `nohup` and returns immediately, so a child that fails a second later leaves the parent's status at 0 with a reassuring "Started 'x' in the background (PID n)" on stdout. Observed with `Invalid virtual machine configuration. Failed to lock auxiliary storage.` appearing only in `~/Library/Logs/lume/<name>.log`. Never treat the PID line as a start signal: poll `lume get … .ipAddress` until it is non-empty, and read the log on timeout.
- **"Failed to lock auxiliary storage" means another lume process holds `nvram.bin`.** Only one `lume run` may hold it, and the create flow's process can outlive the command that started it — so a `--detach` fired immediately after `lume create` races it. `lsof ~/.lume/<name>/nvram.bin` names the holder — NOT `pgrep lume`, which finds unrelated long-lived lume processes and misses this one entirely, because the holder is `com.apple.Virtualization.VirtualMachine` and outlives the command that spawned it. The `CancellationError` pairs printed during create are unrelated and benign: the unattended setup stopping the VM it started. The line meaning success is `Provisioning marker cleared`.
- **A doc grown by appending needs a structural pass, not another append.** `docs/testing-github-workflows-locally.md` had accumulated functions used sections before they were defined, variables referenced far from any declaration, a build procedure split across two headings, and an `## The ubuntu-latest jobs` heading deleted in an earlier edit that left its content orphaned under an unrelated section. Every individual edit had been locally correct. Read the whole file when a section has taken three rounds of edits.

## 2026-07-31 — What proving the lume run phase actually turned up

- **`lume ssh <name> <command>` is a non-login, non-interactive shell, and the run block forgot it.** Homebrew's installer puts `/opt/homebrew/bin` on `PATH` through `~/.zprofile` and `/etc/paths.d`, both of which are login-shell mechanisms, so neither is read. Every remote `brew` call in the baseline build already carried an inline `eval "$(/opt/homebrew/bin/brew shellenv)"` for exactly this reason — but the run-clone block's `act` invocation did not, so the documented production path would have failed with `command not found: act` on a guest where act was installed. The run phase had been marked fixed-but-unproven since the share-path correction; this is what proving it turned up. The failure misleads because an interactive `ssh` into the guest gets a login shell and finds the tools normally: it reads as "works when I look, breaks when I script it."
- **A clone is a point-in-time copy, so a clone taken before provisioning stays unprovisioned.** The first end-to-end attempt failed at `act --version` against a clone made while the baseline still had no Homebrew. Obvious in hindsight, and worth stating in a verification recipe's preconditions rather than leaving to inference — delete and re-clone after any baseline change.
- **`pgrep` does not work inside the agent sandbox**, and it fails in the direction that produces a false negative: `sysmond service not found`, `Cannot get process list`, exit 3. A `pgrep -fq x && echo held || echo clear` idiom therefore reports "clear" for a machine that is not. Reported that as fact once. Use `lsof <specific-file>` when the question is "who holds this", which is both permitted and more precise.

## 2026-08-03 — rumdl counts lines inside fenced code blocks

`MD013` (line length, 118 here) applies to fenced code content, not only to prose — a shell recipe in a ```` ```sh ```` block failed the gate at 122 characters. So a long literal inside a documented command is a real constraint on the literal, not something to suppress: the marker string in the pull-request recipe was shortened to fit rather than the rule disabled. Worth knowing before writing a recipe with a long one-liner in it; `rumdl fmt` will not fix this one, because it cannot reflow code.

## 2026-08-03 — `annotate.sh` across the fleet: eight copies, three generations, one real disposition

No full reconciliation pass has been made. The 2026-08-03 rulings session diffed only the four copies its prompt named, and only for `require_tool`. The maintainer then measured all **eight** (`_dormant/inject_edid`, homebrew-cask-tools, cert-automation, blackoutd, homebrew-babble, zman-didan, bob-book, repo-foundation): three distinct generations, diverging from repo-foundation by 54 to 212 lines. What the comparison actually shows, so the audit does not re-derive it:

- **repo-foundation's copy leads on filetype coverage.** Its `man_re` (`\.[1-9][a-zA-Z]*(\.md)?$`) subsumes the consumers' `\.(1|1\.md)$`; it splits `.plist` and the clang dotfiles into their own rules; it alone carries `require_tool`, `--no-multiprocessing`, and two helper functions. The older copies are behind, not different.
- **One licensing exception:** homebrew-cask-tools hardcodes `--license="GPL-3.0-or-later OR BSD-2-Clause"`. The canonical parameterizes that as `: "${ANNOTATE_LICENSE:=GPL-3.0-or-later}"`, so the first sync would silently start applying GPL-only headers there. `ANNOTATE_LICENSE` is the preferred mechanism (maintainer, 2026-08-03) — set it in that repository rather than forking the script — and the disposition must land **with** the sync, not after it.
- **Fish completions: the first reading of this was wrong twice, and the maintainer caught it.** The claim was that cert-automation's `.fish` rule is dead code because that repository ships no `.fish` files and the canonical would give one an inline `#` header "which is better". Both halves are false. Presence today is the wrong test — `brew generate-tap-man-completions` GENERATES fish completions and man pages in the Homebrew-aligned taps, so the files appear on demand. And an inline header is not better but actively wrong: cert-automation's own comment, three lines above the code that was read, says these files "must keep their generated content intact", and the next generator run destroys an inline header. ## 2026-08-03 — The `--verify` gate would fail on 13 files it already ships

Running the strip-a-copy-and-re-annotate test on a newly written `scripts/main-guard.sh` turned up the divergence on the first try: **`reuse annotate` puts a blank line between the shebang and the SPDX block, and much of this repository does not have one.** Confirmed properly rather than by proxy on `scripts/lint-perms.sh` — strip its block, re-annotate the copy, and the copy comes back with the blank line the committed file lacks. This changes the shape of the queued `annotate.sh --verify` work, so it is recorded before that row is picked up: **the gate cannot simply be turned on.** Landing it means either reshuffling 13 canonical headers in the same change — every one of them synced, so every consumer sees the churn — or landing `--verify` non-gating until a separate pass fixes them. ## 2026-08-04 — The 13 headers are fixed; the strip is where `--verify` will break

All 34 shebang-bearing tracked files now round-trip: strip the SPDX block, re-annotate with the arguments `annotate.sh` passes, and the result is byte-identical to what is committed. Done pre-first-sync deliberately — eleven of the thirteen are canonical or plugin masters, so the same change after the first sync would rewrite a header in every consumer instead of only here. `scripts/annotate.sh` was the odd one out twice over: its block sat 78 lines down at the foot of the documentation header, and without the `#` spacer.

**The strip is the dangerous part, and it failed twice before it worked.** Recorded because `--verify` has to implement exactly this and will meet both:

- A greedy "all leading comment lines after the shebang" match ate **198 lines of documentation across five files** — the SPDX block is not always the first comment, so the pattern must terminate at the block rather than consume everything up to it. Nothing was committed: the damage was caught by `git diff --stat` and reverted with `git restore`. A whitespace-only assertion added afterwards then refused `annotate.sh` correctly instead of mangling it.
- The strip must also remove the blank padding around the block. Leaving it makes every re-annotated file gain a stray blank, so a first check reported **all 34 files as divergent** — a verifier that says everything is broken is as useless as one that says nothing is.

The maintainer's standing requirement is the same lesson from the other side: verify on a BACKUP COPY, never in place, because `reuse annotate` writes.

`--verify` itself is NOT built. The shell case is proven, but the categories that carry the subtle placement bugs — Markdown with YAML frontmatter, and every `--force-dot-license` sidecar case, where "strip and re-annotate" means removing and regenerating a second file — are not, and a verifier with partial coverage gives false confidence exactly where the risk is.

## 2026-08-03 — The synced header had never met YAML frontmatter

`insert_point` in the sync engine already skipped a frontmatter block, so the header landed immediately after the closing `---`. Correct for the loader and wrong for the Markdown gate: the rendered file fails MD071 (no blank line after frontmatter) and then MD012, because the blank line that used to follow the fence ends up under the header's own trailing blank. Latent for as long as it existed — no canonical Markdown source carried frontmatter until the `claude_skills` set (ADR 0025) — and it would have failed the `markdownlint` job in all six consumers at once on the first sync that shipped a skill.

Worth generalizing past the fix: **a canonical file's rendered form in a consumer is a different artifact from its source here, and only the source is under this repository's gates.** `rumdl check` on the source passes; nothing ran the org's own linters over engine *output* until this. The new spec asserts the two structural requirements (a blank line after the fence, no two blank lines in a row) rather than shelling out to rumdl, so it holds wherever the suite runs — but the general gap is that the engine has no "render, then lint the render" coverage for any target type.
